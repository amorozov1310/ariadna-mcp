## 0. Вывод аудита

Функционально UI покрывает всё, что умеет бэкенд. Визуально и структурно
он не готов показываться заказчику: **разворот любой формы разрушает
вёрстку страницы** (U1), фильтр по типам объектов показывает 9 типов из
25+ (U2), настройки подключения к базе размножены по источникам вопреки
реальной модели 1С (U3). Это не косметика — это три функциональных
дефекта, и они определяют приоритет.

Поэтому план — переработка, а не подкрашивание: этап U0 переписывает
оболочку и карточку источника целиком.

## 1. Критические дефекты (P0)

### U1. Разворот формы разрушает вёрстку строки источника

**Симптом** (скриншоты 2 и 3): при клике на «Изменить» или «База» форма
разворачивается внутри строки, а название источника и его метаданные
сжимаются в вертикальную колонку по одному символу в строке — `ma / ma /
re / ✅ / xm / ✅ / in / 20 / 09`. Если открыть обе формы, страница
превращается в кашу. Именно это в первую очередь читается как «выглядит
ужасно».

**Причина** (найдена в коде, не догадка):

```css
.source-item .source-row  { display: flex; gap: 12px; }
.source-item .source-info { flex: 1; min-width: 0; }   /* может сжаться в 0 */
.source-item .source-actions { display: flex; flex-wrap: wrap; }
.source-edit[open] { display: block; width: 100%; }     /* форма внутри flex-строки */
```

`<details>` с формой лежит внутри flex-строки рядом с текстом. При
раскрытии содержимое `.source-actions` становится широким, а
`.source-info` с `min-width: 0` схлопывается до нуля — текст переносится
посимвольно.

**Решение:** формы не должны жить внутри flex-строки. Раскрываемый блок
выносится **под** строку источника на всю ширину карточки (grid-строка
`1fr` во второй ряд), либо — предпочтительно — открывается модальным
окном / отдельной страницей настроек источника. Пункт закрывается в U0.

### U2. Фильтр «Все типы» показывает 9 типов из 25+

**Симптом** (скриншот 4): в выпадающем списке только Справочник,
Документ, РегистрСведений, РегистрНакопления, Перечисление, Отчет,
Обработка, ОбщийМодуль, Подсистема. Отфильтровать по Роли, Константе,
WebСервису, ОбщейКартинке, ФункциональнойОпции, ПланСчетов и прочим —
невозможно, хотя в индексе они есть.

**Причина:** список захардкожен в шаблоне:

```jinja
{% for k in ['Справочник','Документ','РегистрСведений','РегистрНакопления',
             'Перечисление','Отчет','Обработка','ОбщийМодуль','Подсистема'] %}
```
(`src/web/templates/search.html:38`)

**Решение:** заполнять список из реальных данных проекта — те же
`db_stats.kinds`, что дашборд уже показывает (в bshp их 25, в erp — 25+),
отсортировать по количеству, показывать счётчик рядом с типом
(`Справочник 754`). Захардкоженные списки в шаблонах запрещены.

### U3. Настройки базы привязаны к источнику, а не к проекту

**Как есть:** панель «База» (строка подключения, пользователь, пароль,
режим, расписание) продублирована у каждого источника, включая
расширения. У проекта 1idm2 это 12 копий одних и тех же реквизитов
подключения.

**Как должно быть** (уточнение заказчика): расширения лежат в **той же
информационной базе**, что и основная конфигурация. Значит, подключение —
свойство **проекта**, а не источника. У источника остаётся только имя
расширения в этой базе.

**Изменение модели** (`src/core/project_manager.py`):

- `ProjectInfo` получает `dump: DumpConfig` с полями `connect`, `user`,
  `mode`, `schedule`, `last_dump_at` — одна база на проект;
- `SourceInfo.dump` схлопывается до одного поля `extension: str`
  (пусто = основная конфигурация). Остальные поля из `DumpConfig`
  источника удаляются;
- **миграция при загрузке реестра**: если у источника `main` заполнен
  `dump.connect` — перенести connect/user/mode/schedule на проект;
  у остальных источников сохранить только `extension`; пароль в
  `secrets.json` перепривязать с ключа источника на ключ проекта;
- создание задания выгрузки берёт подключение из проекта, а имя
  расширения — из источника;
- `update_source_dump_config()` разделяется на
  `update_project_dump_config()` (подключение) и
  `update_source_extension()` (имя расширения).

**Изменение UI:** блок «Подключение к информационной базе» — один, на
странице настроек проекта. В строке источника — только поле «Расширение
в базе» и кнопка «Обновить из базы». На уровне проекта появляется
главное действие **«Обновить всё из базы»**: выгружает основную
конфигурацию и все расширения из одной базы и переиндексирует проект.

**MCP:** `update_source_from_infobase` сохраняется, плюс добавляется
`update_project_from_infobase(project_id)` для обновления всего проекта.

**Критерий:** у проекта одна строка подключения; добавление расширения
требует ввести только его имя; «Обновить всё из базы» одной кнопкой
обновляет конфигурацию и все расширения.

## 2. Что сохранить

Хорошее в текущем решении, что переработка не должна сломать:

| Что | Почему ценно |
|-----|--------------|
| SSR на Jinja2, без сборки | Мгновенная отдача, нет npm в контуре, деплой одним контейнером. Для инструмента разработчика — верный выбор |
| Дизайн-токены в `:root` | Палитра и радиусы уже в переменных: тема и редизайн делаются правкой токенов, а не переписыванием |
| Полное покрытие функций | Всё, что умеет MCP, доступно из UI |
| Прогрессивное улучшение | Формы работают без JS; long-running операции корректно опрашивают статус |
| Playground | Сильная фича: проверить MCP-инструмент до подключения агента |

## 3. Остальные дефекты

**Идентичность**

- **U4. Нулевая продуктовая идентичность.** Логотипа нет — системный
  текст «1C Scout». Акцент `#4361ee` — узнаваемый дефолтный синий.
  Favicon отсутствует.
- **U5. Эмодзи вместо иконок** — 🔄 🗑 🔌 🔃 ✏ ▶ ✅. Рендерятся по-разному
  в разных ОС, ломают ритм, читаются как незавершённая вёрстка.
  Иконочные кнопки без подписей: «🔄» (переиндексация) и «🗑» (удаление)
  стоят вплотную.

**Навигация**

- **U6. Навигация уникальна на каждой из шести страниц** (проверено по
  всем шаблонам):

  | Страница | Пункты в шапке |
  |----------|----------------|
  | Дашборд | Поиск · Дерево вызовов · Граф · Playground |
  | Поиск | Дашборд · Playground |
  | Дерево вызовов | Дашборд · Поиск · Playground |
  | Граф | Дашборд · Поиск · Дерево (текст) |
  | Карточка объекта | Поиск |
  | Playground | ← Проект · Поиск |

  Набор разделов меняется под пользователем; из карточки объекта нельзя
  попасть в граф, из графа — в playground.
- **U7. Нет подсветки активного раздела.**
- **U8. Нет переключателя проектов** — смена проекта только через «/».

**Читаемость**

- **U9. «Стена» видов метаданных.** 25+ значений одной строкой через `·`
  (скриншот 1) — на мобильном 20 строк сплошного текста. Самый
  информативный блок подан хуже всего.
- **U10. Числа без форматирования:** `534157` вместо `534 157`;
  длительность `391.05` без единиц.
- **U11. Слабая иерархия результатов поиска** — имя, вид, источник и
  синоним почти одного визуального веса.
- **U12. Нет пагинации и полноты выдачи** — «Результаты: 20» без общего
  числа и без «показать ещё». В карточке объекта 118 реквизитов одной
  таблицей без фильтра.

**Надёжность**

- **U13. Нет обработки ошибок.** Во время аудита поиск отдал HTTP 500 и
  показал голое «Internal Server Error» (в логах —
  `sqlite3.OperationalError: unable to open database file`,
  `src/core/db.py:248`, при открытии нового read-соединения). Ошибка
  транзиентная (на 8 повторах не воспроизвелась), но UI на любой сбой
  реагирует стек-трейсом без навигации.
- **U14. Пустая подпись «Флаги модуля:»** — заголовок выводится всегда,
  бейджи только при выставленных флагах; у `Справочник.Номенклатура`
  (erp) все флаги false → подпись без содержимого
  (`object_detail.html:42`).
- **U15. Деструктивные действия равны обычным** — «Удалить проект»
  красной кнопкой в одной строке с «Переиндексировать»; удаление
  источника вплотную к переиндексации. Защита — только `confirm()`.
  Цена промаха: переиндексация ERP ≈ 6.5 минут либо потеря источника.

**Прочее**

- **U16. htmx грузится, но не используется** — `base.html:7` тянет
  `htmx.org@1.9.12` с unpkg на каждой странице, при этом во всех
  шаблонах **ноль** атрибутов `hx-*`. Мёртвая внешняя зависимость.
  Плюс `vis-network` с cdnjs (`graph.html:11`). Для контура 1С-внедрений
  (серверы часто без интернета) любой CDN — риск молчаливой деградации.
- **U17. Нет тёмной темы** при том, что токены уже вынесены.
- **U18. Нет клавиатурных сценариев** — для инструмента «быстро найти»
  нет ни `Ctrl+K`, ни навигации по результатам, ни автофокуса.

## 4. Целевой образ

Поиск — центральный объект интерфейса, а не одна из вкладок. Ориентиры:
Sourcegraph, GitHub code search, Linear. Три принципа:

1. **Одна оболочка на все страницы** — постоянная шапка: проект,
   разделы, глобальный поиск. Контент меняется, каркас нет.
2. **Данные подаются, а не вываливаются** — числа форматируются, перечни
   становятся таблицами и чипами, длинные списки — страничными.
3. **Опасное отделено от частого** — деструктивное уходит в отдельную
   зону с типизированным подтверждением.

## Этап U0. Каркас: критические дефекты + дизайн-система (P0)

Строго первый: остальные этапы наслаиваются на него.

1. **Карточка источника (U1).** Переписать разметку: строка источника —
   grid `[инфо | действия]`, раскрываемая форма — **вторым рядом на всю
   ширину**, либо модальным окном. Убрать `.source-edit[open]{width:100%}`
   из flex-строки. Проверить: открытие обеих форм не деформирует текст.
2. **Модель подключения к базе (U3).** Перенести настройки на уровень
   проекта, у источника оставить «Расширение в базе», добавить действие
   «Обновить всё из базы», написать миграцию реестра (см. раздел 1).
3. **Фильтр типов (U2).** Заполнять из `db_stats.kinds` со счётчиками,
   сортировка по убыванию. Заодно проверить остальные шаблоны на
   захардкоженные перечни.
4. **Токены.** Расширить `:root`: шкалы отступов (`--space-1..6`),
   типографики (`--fs-xs..2xl`), теней. Хардкод-цвета из шаблонов
   (`style="background:#e0e7ff;color:#3730a3"`, `object_detail.html:44-47`)
   вынести в классы-бейджи.
5. **Иконки (U5).** Локальный SVG-спрайт (Lucide/Tabler, ~20 иконок, в
   `static/icons.svg`, не CDN) вместо всех эмодзи. Иконочным кнопкам —
   `aria-label` и `title`.
6. **Идентичность (U4).** SVG-логотип (монограмма + слово), favicon,
   собственная акцентная пара. Предложить 2–3 варианта палитры, применить
   выбранный заказчиком.
7. **Оболочка (U6, U7, U8).** Переписать `base.html`: слева логотип и
   селектор проекта (смена проекта сохраняет текущий раздел); по центру
   постоянный набор — Обзор · Поиск · Граф · Playground · Настройки, с
   подсветкой активного через `{% block active_nav %}`; справа глобальный
   поиск и переключатель темы. **«Дерево вызовов» и «Граф» объединить**
   в раздел «Граф» с переключателем текст/визуал — сейчас это две
   страницы для одной задачи.
8. **Страницы ошибок (U13).** Оформленные 404 и 500 в оболочке проекта:
   понятный текст, кнопка «Назад», детали под `<details>`; FastAPI
   `exception_handler` для `HTTPException` и `Exception`. Отдельно —
   ретрай с backoff в `Database.read_conn()` (3 попытки) на транзиентный
   `unable to open database file`; UI-обработчик обязателен независимо.

**Критерий приёмки:** открытие любых форм не ломает вёрстку (проверить
обе сразу); у проекта одна строка подключения, у источника — только имя
расширения; фильтр типов содержит все виды из индекса со счётчиками;
шапка одинакова на всех страницах с подсветкой активного раздела; эмодзи
в шаблонах не осталось; принудительная ошибка даёт оформленную страницу.

## Этап U1. Поиск (P1) — наибольшая ценность

1. **Иерархия (U11).** Крупно короткое имя, приглушённо префикс вида
   (`Справочник.` серым), ниже мелким синоним; вид и источник — чипами
   справа. Подсветка совпадения через `<mark>`.
2. **Пагинация (U12).** Возвращать общее число; «Показано 20 из 143» +
   «Показать ещё».
3. **Фильтры.** Вид и источник — чипами-переключателями над результатами
   (вместо `<select>`), с быстрым сбросом, состояние в URL (шарить ссылку).
4. **Счётчики на вкладках** — `Метаданные 20 · Процедуры 4 · Код 17`,
   чтобы не переключаться вслепую.
5. **Пустые состояния** — подсказка вместо пустой карточки (проверить
   раскладку, попробовать другую вкладку).
6. Время запроса (`2.1ms`) оставить — хорошая деталь — но как подпись к
   счётчику, а не отдельно по правому краю.

**Критерий:** «Номенклатура» в erp сканируется взглядом за секунды, видно
общее число, фильтр по виду в один клик и отражён в URL.

## Этап U2. Обзор проекта (P1)

1. **Виды метаданных (U9).** Вместо «стены» — таблица-топ с
   горизонтальными барами: вид · количество · доля. Топ-10 + «Показать
   все (25)». Каждая строка — ссылка в поиск с фильтром `kind`.
2. **Метрики (U10).** Разделители тысяч, человекочитаемая длительность
   (`6 мин 31 с`). Плитку «Источников» убрать из метрик — это раздел ниже.
3. **Здоровье индекса.** Вынести на дашборд метрику `diagnose_index`
   (% разрешённых рёбер графа) с цветовой индикацией — сейчас эта
   диагностика доступна только через MCP/playground.
4. **Источники.** Строка: название, тип-бейдж, состояние (отчёт/XML/
   индексация) иконками, относительное время («2 часа назад», полное в
   `title`), действия — в компактное меню «⋯».
5. **Прогресс индексации** — бар вместо текста, с фазой и оценкой
   оставшегося времени.

**Критерий:** дашборд erp читается без стены текста, в том числе на 375px.

## Этап U5. Автономность, тема, клавиатура (P3)

   интернета.

3. **Клавиатура (U18).** `Ctrl+K` / `/` — фокус в глобальный поиск;

   автофокус на главном поле страницы.

   на `--bg` сейчас ниже AA), фокус-стили для кнопок и ссылок.

## Порядок работ

```
U0 (каркас: U1+U2+U3 + дизайн-система + оболочка)
      ├──►  U1 (поиск)          ← наибольшая ценность
      ├──►  U2 (обзор)
      ├──►  U3 (объект и граф)
      ├──►  U4 (безопасность и формы)
      └──►  U5 (автономность, тема, клавиатура)
```

U0 строго первый. Дальше — в порядке ценности: U1, U2, U3, U4, U5.

## Чек-лист запуска (для чата реализации)

Сервер: `docker-compose up -d`, UI — http://localhost:19878. Правка
шаблонов/CSS видна после перезагрузки страницы; правка Python требует
пересборки образа (README, раздел про офлайн-колёса).

### Шаг U0
Промпт: «Выполни этап U0 из docs/UI_IMPROVEMENT_PLAN.md: почини разрушение
вёрстки при раскрытии форм источника (U1), перенеси настройки подключения
к базе на уровень проекта с миграцией реестра и действием „Обновить всё из
базы" (U3), заполняй фильтр типов из db_stats.kinds (U2), затем
дизайн-токены, SVG-иконки вместо эмодзи, логотип и favicon, единая
оболочка base.html с селектором проекта и подсветкой раздела, страницы
404/500 и ретрай в Database.read_conn.»

Проверка: на дашборде bshp открыть «Изменить» и «База» одновременно —
вёрстка цела, текст не переносится посимвольно; у проекта одна строка
подключения, у расширения — только поле имени расширения; в фильтре
поиска присутствуют Роль, Константа, WebСервис со счётчиками;
`grep -P "[\x{1F300}-\x{1FAFF}]" src/web/templates` пусто; шапка
одинакова на всех страницах; `curl localhost:19878/projects/НЕТ` отдаёт
оформленную 404.

## Границы плана

- Бэкенд меняется точечно и только там, где этого требует UI: модель
  `DumpConfig` (U3, с миграцией реестра), обработчики ошибок,
  ретрай соединения, отдача `kinds` и общего числа результатов в поиск.
  Индексация, парсеры, схема индекса и логика графа не затрагиваются.
- Фронтенд-фреймворк и сборка не вводятся: Jinja2 + ванильный JS + один
  CSS — осознанное преимущество, его сохраняем.
- Продукт не переименовывается: «1C Scout» остаётся в MCP, репозитории
  и конфигурации.
