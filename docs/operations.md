# Эксплуатация: готовность, сведения об индексе, перенос и резервная копия

Команды — для запуска в Docker (`docker-compose.yml` из репозитория,
порты по умолчанию). Без Docker индексы лежат рядом с выгрузками в
`data/projects/{проект}/index.db`, остальное так же.

## Что где лежит

| Что | Где | Можно восстановить из другого? |
| --- | --- | --- |
| Реестр проектов и источников | `data/projects.json` | нет — копировать обязательно |
| Выгрузки (XML) | `data/projects/{проект}/sources/{источник}/` | нет — или выгрузить из конфигуратора заново |
| Словарь проекта (слова пользователей → объекты) | `data/projects/{проект}/glossary.json` | нет — копировать обязательно |
| Индексы SQLite | том `ariadna-index` (`/index/{проект}/index.db`) | да — `reindex` по выгрузкам |
| Наборы оценки поиска | `data/eval/` (если есть) | нет |

Индекс — производные данные: всё в нём строится из выгрузок. Копировать его
стоит только ради времени: на крупной конфигурации полная переиндексация —
десятки минут, копия тома — минуты.

## Справка платформы

Для каждой версии платформы Ариадна хранит один индекс для всех проектов.
В Docker это `/index/platform-help/<версия>/help.db` на томе `ariadna-index`.
При нативном запуске файл лежит в `<DATA_DIR>/platform-help/<версия>/help.db`.
Если задан `INDEX_DIR`, каталог `platform-help` находится в нём.

В меню настроек сервера откройте **Справка платформы**. Укажите полную версию
и загрузите `shcntx_ru.hbk` из каталога платформы. Чтобы агент мог искать также
по языку запросов, добавьте `shquery_ru.hbk` от той же версии. При повторной
загрузке прежняя справка доступна до завершения построения. При запуске
Ариадна ищет книги в доступных ей каталогах и обновляет устаревшие индексы
в фоне. При нативном запуске она проверяет стандартные каталоги установки.
Для нестандартной установки задайте `ARIADNA_PLATFORM` с путями к каталогам
платформы. Разделитель путей — `;` в Windows и `:` в Linux.

В Docker установка платформы на хосте становится доступна после подключения
её каталога к контейнеру. Например, добавьте рядом с `docker-compose.yml`
файл `docker-compose.override.yml` и замените путь и версию на свои:

```yaml
services:
  ariadna:
    environment:
      ARIADNA_PLATFORM: /platform
    volumes:
      - type: bind
        source: 'C:\Program Files\1cv8\8.3.27.2170\bin'
        target: /platform/8.3.27.2170/bin
        read_only: true
```

Оставьте полный номер версии в пути внутри контейнера: по нему Ариадна
определяет версию книги. Docker Desktop должен иметь доступ к каталогу
хоста, а процесс в контейнере — права на чтение файлов в подключённом
каталоге. Примените настройки командой `docker compose up -d`. Если Docker
не может читать этот каталог, загрузите `.hbk` через Web UI описанным выше
способом. Для ручной загрузки подключать каталог платформы не требуется.

Для переноса одной версии откройте **Настройки сервера → Справка платформы**
и нажмите **Скачать** в строке нужной версии. На другой установке выберите
полученный `help-<версия>.db` в разделе **Загрузить готовый индекс**.
Версия указана внутри файла.
Для резервной копии всех версий сохраните каталог `platform-help` вместе с томом.
Пометка «Индекс устарел» означает, что изменился разборщик или схема индекса.
Если индекс устарел или повреждён, загрузите книги заново или перенесите
свежий индекс. Для привязки проекта откройте
**Настройки проекта → Общее → Версия платформы**. Удаление справки
затрагивает все проекты с этой версией.

### Проверка вызовов платформы

`check_platform_calls(project_id="demo", limit=50, offset=0)` проверяет процедуры,
функции и основной код проиндексированных модулей. Чтобы проверить только расширение, передайте
его `source_id`. Ариадне нужны исходные BSL-файлы. Для изменённого файла в ответе
будет подсказка обновить индекс. Код внутри `#Удаление` пропускается. Лимит страницы —
500 замечаний. Готовый отчёт показывает число модулей, ошибок, предупреждений
и непроверенных вызовов. При каждой выдаче Ариадна сверяет время изменения
и размер всех файлов выбранных источников. Если исходники изменились или
пропали, ответ предупреждает об устаревших счётчиках и показывает до пяти путей.
Выполните `reindex`, чтобы обновить отчёт.

Чтобы сразу получить ошибки, передайте `level="error"`. Допустимы также
`"warning"`, `"unchecked"` и список уровней. Фильтр применяется перед `offset`
и `limit`, счётчики отражают весь отчёт по выбранным источникам.

Инструмент ищет точное русское или английское имя в справке выбранной сборки.
Он распознаёт прямое обращение к менеджеру метаданных, глобальное свойство с одним
типом, переменную после присваивания `Новый Тип` и её свойство с единственным
типом по справке, если метод этого свойства известен. Неоднозначная граница
оператора, неизвестный тип и неизвестный состав методов дают «Не проверено».
Вызовы процедур общих модулей проверяет `find_broken_calls`. Оба инструмента
находят обращения к неэкспортным методам менеджера из других модулей и
к отсутствующим справочникам, документам и константам при наличии метаданных.
Если хотя бы один источник проиндексирован старой версией парсера,
`check_platform_calls` попросит выполнить `reindex` всего проекта.

Режим берётся из `Configuration.xml` основной конфигурации, в том числе при
проверке расширения. Нижняя граница — большее из версии появления API
и указанного в справке минимального режима. Для известных функций без
явного ограничения справки проверенная на платформе граница имеет приоритет.
Оба инструмента используют одну границу. При `DontUse` или отсутствии
режима в метаданных сравнение пропускается. Предупреждение о контексте
выдаётся, когда директива процедуры и активные ветки препроцессора
однозначно указывают на клиент, а справка перечисляет только серверные
контексты и внешнее соединение.

Если справка загружена, переиндексация готовит полный отчёт и сохраняет
`platform-check.zip` рядом с `index.db` (для Docker — на томе
`ariadna-index`). Из него читаются и страницы по отдельным источникам.
После загрузки или замены справки Ариадна готовит отчёты в фоне для готовых
проектов, которые используют эту версию. После удаления справки Ариадна
заново проверяет автовыбор и сохраняет снимок для оставшейся версии.
При завершении переиндексации Ариадна сверяет выбранную справку ещё раз.
Пересборка или удаление справки и смена режима совместимости делают прежний
снимок неприменимым. Если нужного
снимка ещё нет, первый запрос запускает его построение в фоне. Повторите
вызов через минуту-две, чтобы получить страницу готового отчёта.

## Готовность: `/health` и `/ready`

- `GET /health` — процесс жив, Web UI отвечает. Индексы не читает; его
  проверяет healthcheck контейнера. `200 {"status": "ok"}`.
- `GET /ready` — проекты готовы отвечать на запросы: `200`, если готовы
  все, `503` — если хоть один переиндексируется, завершился ошибкой или не
  проиндексирован. Пустой реестр — `200`.
- `GET /ready?project=demo` — один проект: `200` / `503`, `404` — проекта
  нет.

```bash
curl -s http://127.0.0.1:19878/ready?project=demo
```

```json
{"id": "demo", "status": "indexing", "ready": false,
 "reason": "идёт переиндексация",
 "progress": {"progress_phase": "bsl", "progress_current": 1200, "progress_total": 5400}}
```

`/ready` читает только реестр и одну строку состояния индекса — его можно
опрашивать хоть раз в секунду, в том числе во время переиндексации.
Ожидание готовности в скрипте:

```bash
until curl -sf "http://127.0.0.1:19878/ready?project=demo" >/dev/null; do sleep 5; done
```

Агенту то же самое показывает MCP-инструмент `get_index_status`.

## Сведения об индексе: `/api/projects/{id}/manifest`

Из чего и чем построен индекс — чтобы внешний клиент решил, свежий ли он,
не читая логи:

```bash
curl -s http://127.0.0.1:19878/api/projects/demo/manifest
```

- `ariadna_version`, `schema_version` (формат самого манифеста);
- `status`, `ready`; `index` — состояние, время последней индексации и
  итоговые числа (объекты, модули, процедуры, вызовы);
- `formats` — отпечаток парсера BSL и формат поисковых карточек **текущей**
  версии сервера;
- `sources` — по источнику: тип, имя и версия конфигурации, откуда
  метаданные (`xml` — `Configuration.xml`, `report` — отчёт по
  конфигурации), время индексации, число модулей, отпечаток парсера, которым
  разобран код (`parser_current` — совпадает ли с текущим), последний
  полный разбор и его причина, покрытие поисковыми карточками
  (`modules_with_code` — модулей с процедурами, `modules_current` — с
  карточками текущего формата);
- `issues` — что требует переиндексации: источник разобран другой версией
  парсера, карточки построены не для всех модулей, источник не
  проиндексирован. Пусто — индекс соответствует версии сервера.

После обновления Ариадны `issues` подсказывает, нужна ли переиндексация;
сама переиндексация разбирает заново только то, что нужно (изменившиеся
модули, а при смене парсера — источник целиком).

## Резервная копия

1. Скопировать `data/` (реестр, выгрузки). Это можно делать и на работающем
   сервере, если в это время не добавляют и не меняют источники.
2. По желанию — индексы, при **остановленном** контейнере (SQLite в режиме
   WAL: копия файла на ходу может оказаться несогласованной):

```bash
docker compose stop
docker run --rm --entrypoint tar -v ariadna-index:/index -v "$PWD/backup:/backup" ariadna czf /backup/ariadna-index.tgz -C /index .
docker compose start
```

На Windows — из PowerShell, `$PWD` там тоже работает; из Git Bash перед
командой нужен `MSYS_NO_PATHCONV=1`, иначе пути в `-v` испортятся.

## Восстановление и перенос на другую машину

1. Склонировать репозиторий той же или более новой версии и подготовить
   образ ([SETUP.md](../SETUP.md), шаги 1–2).
2. Положить сохранённый `data/` в каталог клона.
3. Индексы — одно из двух:
   - **пересобрать**: `docker compose up -d --build`, затем `reindex`
     каждого проекта (Web UI или MCP). Если в `data/` остались
     `projects/*/index.db` от запуска без Docker, на пустой том при старте
     перенесутся они — `reindex` обновит их до текущих выгрузок;
   - **восстановить из копии** — до первого запуска:

```bash
docker volume create ariadna-index
docker run --rm --entrypoint tar -v ariadna-index:/index -v "$PWD/backup:/backup" ariadna xzf /backup/ariadna-index.tgz -C /index
docker compose up -d
```

4. Проверить: `curl http://127.0.0.1:19878/ready` — `200`, в манифесте
   каждого проекта `issues` пуст. Если нет — `reindex` проекта.

Индекс переносим между машинами и ОС: пути к модулям в нём относительные
(от корня выгрузки), а выгрузка ищется по реестру. Индекс более старой
версии Ариадны подходит: при изменении парсера или формата карточек
следующий `reindex` пересоберёт нужное сам; индекс несовместимой схемы
открывается пустым — его заполнит `reindex`.

Если в `projects.json` путь к выгрузке абсолютный (правили вручную), на
новой машине он должен существовать — или выгрузку нужно положить в
`data/projects/{проект}/sources/{источник}/xml/` и поправить путь.

## Индекс с нуля

- Один проект — `reindex` (разбирает только изменившееся) или удалить и
  создать проект заново.
- Все индексы Docker:

```bash
docker compose down
docker volume rm ariadna-index
docker compose up -d
```

затем `reindex` проектов. Выгрузки и реестр при этом не затрагиваются.
