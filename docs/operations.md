# Эксплуатация: готовность, сведения об индексе, перенос и резервная копия

Команды — для запуска в Docker (`docker-compose.yml` из репозитория,
порты по умолчанию). Без Docker индексы лежат рядом с выгрузками в
`data/projects/{проект}/index.db`, остальное так же.

## Что где лежит

| Что | Где | Можно восстановить из другого? |
| --- | --- | --- |
| Реестр проектов и источников | `data/projects.json` | нет — копировать обязательно |
| Выгрузки (XML, отчёт) | `data/projects/{проект}/sources/{источник}/` | нет — или выгрузить из конфигуратора заново |
| Индексы SQLite | том `ariadna-index` (`/index/{проект}/index.db`) | да — `reindex` по выгрузкам |
| Наборы оценки поиска | `data/eval/` (если есть) | нет |

Индекс — производные данные: всё в нём строится из выгрузок. Копировать его
стоит только ради времени: на крупной конфигурации полная переиндексация —
десятки минут, копия тома — минуты.

## Готовность: `/health` и `/ready`

- `GET /health` — процесс жив, Web UI отвечает. Индексы не читает; его
  проверяет healthcheck контейнера. `200 {"status": "ok"}`.
- `GET /ready` — проекты готовы отвечать на запросы: `200`, если готовы
  все, `503` — если хоть один переиндексируется, завершился ошибкой или не
  проиндексирован. Пустой реестр — `200`.
- `GET /ready?project=demo` — один проект: `200` / `503`, `404` — проекта
  нет.

```bash
curl -s http://127.0.0.1:19878/ready?project=demo
```

```json
{"id": "demo", "status": "indexing", "ready": false,
 "reason": "идёт переиндексация",
 "progress": {"progress_phase": "bsl", "progress_current": 1200, "progress_total": 5400}}
```

`/ready` читает только реестр и одну строку состояния индекса — его можно
опрашивать хоть раз в секунду, в том числе во время переиндексации.
Ожидание готовности в скрипте:

```bash
until curl -sf "http://127.0.0.1:19878/ready?project=demo" >/dev/null; do sleep 5; done
```

Агенту то же самое показывает MCP-инструмент `get_index_status`.

## Сведения об индексе: `/api/projects/{id}/manifest`

Из чего и чем построен индекс — чтобы внешний клиент решил, свежий ли он,
не читая логи:

```bash
curl -s http://127.0.0.1:19878/api/projects/demo/manifest
```

- `ariadna_version`, `schema_version` (формат самого манифеста);
- `status`, `ready`; `index` — состояние, время последней индексации и
  итоговые числа (объекты, модули, процедуры, вызовы);
- `formats` — отпечаток парсера BSL и формат поисковых карточек **текущей**
  версии сервера;
- `sources` — по источнику: тип, имя и версия конфигурации, откуда
  метаданные (`xml` — `Configuration.xml`, `report` — отчёт по
  конфигурации), время индексации, число модулей, отпечаток парсера, которым
  разобран код (`parser_current` — совпадает ли с текущим), последний
  полный разбор и его причина, покрытие поисковыми карточками
  (`modules_with_code` — модулей с процедурами, `modules_current` — с
  карточками текущего формата);
- `issues` — что требует переиндексации: источник разобран другой версией
  парсера, карточки построены не для всех модулей, источник не
  проиндексирован. Пусто — индекс соответствует версии сервера.

После обновления Ариадны `issues` подсказывает, нужна ли переиндексация;
сама переиндексация разбирает заново только то, что нужно (изменившиеся
модули, а при смене парсера — источник целиком).

## Резервная копия

1. Скопировать `data/` (реестр, выгрузки). Это можно делать и на работающем
   сервере, если в это время не добавляют и не меняют источники.
2. По желанию — индексы, при **остановленном** контейнере (SQLite в режиме
   WAL: копия файла на ходу может оказаться несогласованной):

```bash
docker compose stop
docker run --rm --entrypoint tar -v ariadna-index:/index -v "$PWD/backup:/backup" ariadna czf /backup/ariadna-index.tgz -C /index .
docker compose start
```

На Windows — из PowerShell, `$PWD` там тоже работает; из Git Bash перед
командой нужен `MSYS_NO_PATHCONV=1`, иначе пути в `-v` испортятся.

## Восстановление и перенос на другую машину

1. Склонировать репозиторий той же или более новой версии и подготовить
   образ ([SETUP.md](../SETUP.md), шаги 1–2).
2. Положить сохранённый `data/` в каталог клона.
3. Индексы — одно из двух:
   - **пересобрать**: `docker compose up -d --build`, затем `reindex`
     каждого проекта (Web UI или MCP). Если в `data/` остались
     `projects/*/index.db` от запуска без Docker, на пустой том при старте
     перенесутся они — `reindex` обновит их до текущих выгрузок;
   - **восстановить из копии** — до первого запуска:

```bash
docker volume create ariadna-index
docker run --rm --entrypoint tar -v ariadna-index:/index -v "$PWD/backup:/backup" ariadna xzf /backup/ariadna-index.tgz -C /index
docker compose up -d
```

4. Проверить: `curl http://127.0.0.1:19878/ready` — `200`, в манифесте
   каждого проекта `issues` пуст. Если нет — `reindex` проекта.

Индекс переносим между машинами и ОС: пути к модулям в нём относительные
(от корня выгрузки), а выгрузка ищется по реестру. Индекс более старой
версии Ариадны подходит: при изменении парсера или формата карточек
следующий `reindex` пересоберёт нужное сам; индекс несовместимой схемы
открывается пустым — его заполнит `reindex`.

Если в `projects.json` путь к выгрузке абсолютный (правили вручную), на
новой машине он должен существовать — или выгрузку нужно положить в
`data/projects/{проект}/sources/{источник}/xml/` и поправить путь.

## Индекс с нуля

- Один проект — `reindex` (разбирает только изменившееся) или удалить и
  создать проект заново.
- Все индексы Docker:

```bash
docker compose down
docker volume rm ariadna-index
docker compose up -d
```

затем `reindex` проектов. Выгрузки и реестр при этом не затрагиваются.
