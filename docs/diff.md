# Отличия от типовой и подготовка к обновлению

Ариадна сравнивает индексы проектов. Это даёт два ответа:

1. **Что доработано** в вашей конфигурации относительно типовой: новые
   объекты и реквизиты, изменённые и добавленные процедуры типовых модулей и
   текст каждой правки.
2. **Где будет ручное слияние при обновлении** на новый релиз типовой: места,
   которые тронуты и вашими доработками, и изменениями релиза.

Выгрузки для сравнения не нужны — сравниваются готовые индексы. Только текст
процедур (diff) читается из файлов выгрузок обоих проектов.

## Три проекта

Всё это необязательно: без базы и нового релиза проект работает как обычно —
поиск, граф вызовов, код. База нужна для «Что доработано», новый релиз — для
«Обновления на новый релиз» (вместе с базой).

| Проект | Что в нём | Где задаётся |
|---|---|---|
| **Ваш проект** | выгрузка вашей (доработанной) конфигурации | обычный проект |
| **База** | выгрузка типовой **того же релиза**, что и ваша конфигурация | «Доработки → Изменить сравнение» или «Настройки проекта → Сравнение с типовой» в Web UI |
| **Новый релиз** | выгрузка типовой, на которую предстоит обновление | там же, необязательно |

База и новый релиз — обычные проекты Ариадны: создайте проект, загрузите
выгрузку типовой из Конфигуратора, проиндексируйте. Если выгрузка уже лежит в
`data/`, источник может указывать на неё по пути.

Пример: ваша конфигурация — 2.5.12 с доработками. База — проект с типовой
2.5.12. Новый релиз — проект с типовой 2.6.1.

```
База (типовая 2.5.12) ──► Ваш проект (2.5.12 + доработки)      = «Что доработано»
База (типовая 2.5.12) ──► Новый релиз (типовая 2.6.1)          = изменения релиза
                          пересечение двух списков              = «Обновление на новый релиз»
```

## Порядок работы

1. **Заведите базу** — проект с типовой того же релиза, что и ваш проект, — и
   выберите её в «Доработки → Изменить сравнение» (или в настройках проекта). Если ваш проект ещё не
   проиндексирован, первая индексация возьмёт индекс базы за основу и
   переразберёт только отличающиеся модули — это в разы быстрее.
2. **«1. Что доработано»** — сводка и доработанные типовые объекты (больше
   изменений — выше), новые и удалённые объекты. Раскройте объект — его новые
   реквизиты с типами и изменённые процедуры по модулям; щелчок по процедуре —
   diff её текста «было в типовой → стало у вас».
3. **Вышел новый релиз** — заведите проект с его типовой и выберите «Новым
   релизом». **«2. Обновление на новый релиз»** покажет пересечения:

   | Вид | Что делать |
   |---|---|
   | Правили и вы, и релиз | слить вручную; отмечено, если релиз сменил сигнатуру |
   | Вы правили — в релизе удалено | найти, куда релиз перенёс код, и перенести правку |
   | Перехвачено в расширении — в релизе удалено | перехват перестанет применяться: перенести на новое место |
   | Перехвачено в расширении — релиз изменил | для `&Вместо` изменения релиза не выполнятся — перенести их в расширение; сменилась сигнатура — переписать перехват |
   | Вы добавили — в релизе появилось с тем же именем | переименовать своё: после обновления будет дубль |
   | Вы удалили — релиз изменил | решить, нужно ли удаление |
   | Объект / модуль меняли оба, но разные места | для сведения, обычно сливается само |

   Щелчок по процедуре — обе правки рядом: ваша и релиза, каждая как diff от
   базы, и перехваты этой процедуры в расширениях проекта с их кодом.
   Расширения — источники проекта вида «Расширение»: их перехваты
   (`&Вместо`, `&После`, `&Перед`, `&ИзменениеИКонтроль`) Ариадна находит сама,
   как и перехваты событий заимствованных форм — обработчики с «Перед»,
   «После» или «Вместо» в свойствах формы расширения (`callType` в Form.xml).
4. **После обновления** вашей конфигурации загрузите её новую выгрузку в ваш
   проект и выберите базой проект нового релиза — поле «Новый релиз» очистится
   само. Проект старой типовой больше не нужен.

## Отчёт файлом

У сводок обоих разделов есть кнопки «Скачать»:

- **Excel (CSV)** — таблица, открывается в Excel двойным щелчком (UTF-8,
  разделитель «;»). В «Что доработано» строка — одно изменение (процедура,
  реквизит, форма, модуль). В «Обновлении» строка — одно пересечение с
  подсказкой «Что делать» и пустыми колонками «Решение» и «Ответственный» —
  удобно распределить слияние между разработчиками.
- **Markdown** — тот же отчёт текстом; пересечения обновления — чек-лист
  `- [ ]`, который можно положить в задачу или wiki.

## Какие версии сравниваются

Шапка раздела «Доработки» показывает все три проекта с версиями из их индексов.
Если версии вашего проекта и базы различаются, выводится предупреждение: в
«Что доработано» попадут и изменения типовой между этими релизами — базой
должна быть типовая того же релиза.

## Для агента (MCP)

- `diff_from_base` — то же, что «Что доработано». Без параметров — сводка (в
  первой строке — какие версии сравниваются); `object_name` — всё по объекту;
  `module_name` + `procedure_name` — diff текста процедуры.
- `update_conflicts` — то же, что «Обновление на новый релиз».
  `release_project=""` берёт новый релиз из настроек проекта, иначе — id
  проекта с новой типовой; `object_name` сужает до объекта; `module_name` +
  `procedure_name` — обе правки процедуры.

Типичные вопросы агенту: «что доработано в документе ЗаказКлиента», «правили
ли мы процедуру ОтразитьРезерв», «какие наши доработки затронет обновление и
что придётся сливать руками».
