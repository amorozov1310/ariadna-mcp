## Этап 1. Корректность графа вызовов (D1–D4, D9)

Ядро всей работы. Принцип: **эвристики заменяются резолвингом по факту** —
индекс сам знает, какие общие модули и менеджеры существуют.

### 1.1. Двухпроходная индексация BSL

`src/core/indexer.py` (`index_bsl`), `src/core/bsl_parser.py`:

- **Проход 1**: собрать по всем источникам проекта множества:
  - имена общих модулей (`ОбщийМодуль.*` → короткое имя, например
    `ДокументооборотИнтеграция`);
  - имена объектов по видам (для менеджерных вызовов `Catalogs.Items.Method()`).
- **Проход 2**: парсинг файлов. Классификация `X.Y(` :
  - `X` — известный общий модуль → межмодульный вызов (независимо от
    «переменных» префиксов);
  - `X` — известный менеджер (`Справочники`/`Catalogs`, ...) → менеджерный вызов;
  - иначе — переменная, пропустить.
- **Удалить** `_VARIABLE_PREFIXES` и `_VARIABLE_PATTERNS` полностью
  (вместе с хардкодом pro100agro). `islower()`-эвристику можно оставить
  как последний фильтр для неизвестных имён.
- **Локальные вызовы** (D2): при парсинге модуля известен список его же
  процедур (первый result.procedures прохода по файлу). Если имя из
  платформенного стоп-листа совпадает с процедурой этого модуля —
  это вызов, не выбрасывать. Стоп-лист применять только к именам,
  которых нет ни в текущем модуле, ни в множестве экспортных процедур.
- В `calls` записывать также `caller_module` не нужно (есть через join),
  но нужна новая колонка `callee_kind` (`local` | `common_module` | `manager`).

### 1.2. Таблица разрешённых рёбер

`src/core/db.py` — новая таблица:

```sql
CREATE TABLE calls_resolved (
    call_id   INTEGER REFERENCES calls(id) ON DELETE CASCADE,
    callee_id INTEGER REFERENCES procedures(id) ON DELETE CASCADE,
    confidence TEXT DEFAULT 'exact'   -- exact | module_fuzzy | name_only
);
CREATE INDEX idx_cr_callee ON calls_resolved(callee_id);
```

Резолвинг после прохода 2 (батчем, executemany):
- `local` → процедура того же модуля; если нет — экспортная одноимённая
  (глобальные модули), confidence=`name_only`;
- `common_module` → процедура модуля с этим коротким именем; при наличии
  в нескольких источниках — приоритет расширения над main (расширение
  перекрывает);
- `manager` → процедура соответствующего `МодульМенеджера`.

Неразрешённые вызовы остаются без строки в `calls_resolved` — это
нормально (вызовы платформы/внешних компонент) и измеримо (этап 7).

### 1.3. Построение деревьев по FK

`src/core/call_analyzer.py`:
- `_build_down`: children = join `calls` → `calls_resolved` → `procedures`.
  Убрать `LIMIT 1`-запросы (D4).
- `_build_up`: callers = join в обратную сторону по `callee_id` конкретной
  процедуры (D3). Матч по имени остаётся только как fallback для вызовов
  без резолва, с пометкой `?` в выводе.
- В текстовом выводе помечать нерезолвленные узлы (`~ВозможноПлатформа`),
  чтобы агент видел уровень доверия.

### 1.4. Директивы расширений (D9)

`src/core/bsl_parser.py`:
- Распознавать `&Вместо("Имя")`, `&После("Имя")`, `&Перед("Имя")`,
  `&ИзменениеИКонтроль("Имя")` и EN `&Around/&After/&Before/&ChangeAndValidate`
  как директиву следующей процедуры: писать в `procedures.directive`
  (например `&Вместо:ПровестиДокумент`) и **не** извлекать из этой строки вызовы.
- В `calls_resolved` для процедур-перехватчиков добавлять ребро
  «перехватывает» к целевой процедуре основной конфигурации
  (можно как обычное ребро с confidence=`override`), чтобы дерево «вверх»
  у метода main-конфигурации показывало перехватчики расширения.
- `ПродолжитьВызов(...)` / `ProceedWithCall(...)` внутри `&Вместо` —
  распознавать как ребро к перехваченной процедуре.

Критерии приёмки этапа 1 (тесты на фикстурах RU и EN):
- вызов `ДокументооборотИнтеграция.X()` присутствует в графе;
- локальный вызов `ПроверитьЗаполнение()` при наличии одноимённой процедуры в модуле — в графе;
- up-дерево `ЦеныСервер.РассчитатьЦену` НЕ содержит вызывающих `СкидкиСервер.РассчитатьЦену`;
- down-дерево: локальный вызов резолвится в свой модуль, а не в чужой;
- `&Вместо` не порождает ребро `Вместо()`; перехватчик виден в up-дереве цели.

## Этап 4. Индексация: асинхронность и инкрементальность (D7)

1. **Фоновая индексация**: `ProjectManager.reindex_async()` — поток +
   статусы `indexing (N/M files)` в `index_state` (колонки
   `progress_current`, `progress_total`, `progress_phase`).
   MCP `reindex` возвращает немедленно: `Reindex started, track via
   get_index_status`. Web UI — опрос статуса (эндпоинт уже есть).
   Одновременно два reindex одного проекта — запрещены (замок в PM).
2. **Инкрементальность**: перед проходом 2 сравнивать `file_hash`
   (уже хранится в `modules.file_hash`); неизменённые файлы пропускать
   (их procedures/calls не трогать). Резолвинг рёбер (1.2) при этом
   пересчитывать целиком — он дешёвый (SQL-джойны).
3. **Батчи**: все вставки procedures/calls/fts — `executemany` пачками
   по 1000; одна транзакция на файл-пачку, `PRAGMA synchronous=OFF`
   на время индексации.
4. **Отдельное соединение на поток**: сейчас одно соединение
   `check_same_thread=False` делится между web/MCP/индексатором —
   выдавать read-соединения per-thread (`threading.local`), писатель один.
5. **Баг D15 — мусорный `duration_sec` (чинить первым, до остальных
   пунктов этапа)**: в `Indexer.index_bsl` переменная замера `start`
   (`start = time.time()` в начале метода) затем перезатирается циклом
   привязки вызовов `for (start, end), pid in proc_id_map.items():`,
   поэтому итоговое `time.time() - start` даёт ~epoch-время (~1.79e9 сек)
   на каждый источник — отсюда `duration_sec` в миллиарды секунд в
   `data/projects.json` (bshp: 2 источника ≈ 3.58e9; 1idm2: 12 ≈ 21.5e9).
   Исправление: переименовать переменные цикла (например
   `p_start, p_end`) — и проверить весь модуль на другие затенения
   `start`/`end`. Испорченные значения в projects.json сами исправятся
   при следующем reindex. Регрессия: в slow-тестах индексации добавить
   `assert stats.duration_sec < 3600`.

Критерий: индексация ERP-выгрузки завершается без таймаута MCP;

## Этап 6. Эргономика MCP

1. **Транспорт и SDK**: добавить streamable HTTP (SSE в спецификации MCP
   deprecated; Claude Code поддерживает оба). SSE оставить на старом порту
   для совместимости. **Важно**: 2026-09-03 контейнер падал из-за
   незапинованной зависимости — pip установил mcp SDK 2.1.1, где у
   низкоуровневого `Server` удалены декораторы `list_tools()`/`call_tool()`
   и SSE-транспорт в старом виде отсутствует. Временный хотфикс — пин
   `mcp>=1.0,<2` в Dockerfile и pyproject.toml. В рамках этого этапа
   мигрировать `src/mcp_server/server.py` на API mcp 2.x (или FastMCP),
   после чего пин снять/поднять до `>=2,<3`.
   Второй хотфикс там же: `handle_sse` в `src/main.py` не возвращал
   `Response` → `TypeError: 'NoneType' object is not callable` в логах
   при каждом отключении SSE-клиента (известный баг примера SDK 1.x,
   modelcontextprotocol/python-sdk#1099); исправлено возвратом пустого
   `Response()`. При миграции на streamable HTTP этот код уходит целиком —
   не потерять фикс, если SSE-эндпоинт останется для совместимости.
2. **Аннотации инструментов**: `readOnlyHint: true` на все поисковые.
   `remove_source` (D13) остаётся в MCP (решение заказчика), но с двумя
   предохранителями: аннотация `destructiveHint: true` (клиент показывает

   инструмент удаляет и файлы источника, и данные индекса необратимо.
3. **`set_active_project` (D12)**: удалить. Вместо него — если в реестре
   ровно один проект, `project_id` во всех инструментах становится
   опциональным (дефолт — единственный проект). Ошибка при отсутствии
   `project_id` и >1 проекта должна перечислять доступные id (уже так).
4. **Бюджет токенов**:
   - `get_object_details`: параметр `detail` = `brief` (по умолчанию:
     счётчики + первые 30 реквизитов + список ТЧ без состава) | `full`;
   - `list_objects`, `find_references`, `search_*`: параметры
     `limit`+`offset`, в конце выдачи `... use offset=N for more`;
   - `get_call_tree`: жёсткий лимит узлов (например 200) с пометкой
     об усечении; параметр `max_nodes`.
5. **Описания инструментов** — переписать с подсказками агенту, когда что
   использовать (это напрямую влияет на выбор инструмента моделью), напр.:
   - `search_metadata`: «Первый шаг при любом вопросе про объект. ...»
   - `get_call_tree`: «Кто вызывает / что вызывает процедура. Для „где
     используется реквизит" используй find_references.»
   - `search_code`: «Полнотекстовый grep по BSL. Для поиска процедуры по
     имени используй search_procedures.»
   Убрать префиксы `[Фаза 2]` из описаний (агенту они ничего не говорят).
6. **Единый формат ответа**: сейчас plain text — оставить (компактно для

Критерий: чек-лист ручной проверки из Claude Code — типовые сценарии

## Этап 8. Автовыгрузка из информационной базы (кроссплатформенно)

> **УДАЛЕНО 2026-09-15.** Этап был реализован и затем убран целиком:
> платформы 1С внутри контейнера нет, поэтому выгрузку приходилось
> выполнять отдельным агентом на хосте — держать ради этого постоянно
> запущенный процесс оказалось сложнее, чем выгрузить XML из
> Конфигуратора руками и нажать «Переиндексировать». Код удалён без
> возможности восстановления; раздел ниже оставлен как история решения.

Цель: полный цикл «база → XML-выгрузка → индекс» без ручных шагов,
работающий при любом развёртывании: сервер в Docker (Linux) или нативно,
платформа 1С — на Windows или Linux, база — файловая или клиент-серверная.

Ключевое решение: сервер НЕ вызывает `1cv8` сам — выгрузку выполняет
**агент**, отдельный кроссплатформенный Python-скрипт на машине с
платформой. Сервер ведёт очередь заданий; Web UI / MCP / планировщик
только создают задания.

1. **Настройки подключения источника** (в `sources[]` реестра):
   `dump: {connect: "File=D:\\bases\\erp" | "Srvr=srv1c;Ref=erp",
   user: "...", extension: "" | "<ИмяРасширения>", schedule: "" | cron,
   mode: "agent" | "local"}`. Пароль — НЕ в projects.json: отдельный
   `data/secrets.json` (вне git, маскирование в UI и логах).
2. **Очередь заданий**: таблица/JSON `dump_jobs` (id, project, source,
   status: pending/running/done/failed, лог, created/finished). HTTP API:
   `POST /api/dump-jobs` (создать), `GET /api/dump-jobs?status=pending`
   (агент забирает, с авторизацией по токену агента), `POST
   /api/dump-jobs/{id}/result`. После `done` сервер автоматически
   запускает reindex источника (инкрементальный, этап 4).
3. **Агент `scripts/dump_agent.py`** — один скрипт для Windows и Linux,
   без внешних зависимостей (stdlib): цикл опроса очереди → запуск
   `1cv8 DESIGNER <connect> /N<user> /P<pass> /DumpConfigToFiles <dir>
   -update /DisableStartupDialogs /DisableStartupMessages /Out <log>`
   → отчёт о результате. Путь к бинарнику: параметр `--platform-path`
   или автопоиск (Windows: свежайший `C:\Program Files\1cv8\*\bin\
   1cv8.exe`; Linux: `/opt/1cv8/x86_64/*/1cv8`). Результат кладётся в
   каталог источника: общий volume, если агент видит `data/` (типовой
   случай — агент на том же хосте, где Docker), иначе — загрузка zip
   через существующий upload-эндпоинт Web UI.
4. **Режим `local`**: если сервер запущен нативно на машине с платформой,
   он исполняет задание сам тем же кодом (общий модуль
   `src/core/config_dumper.py`, используемый и агентом, и сервером).
   В Docker режим `local` недоступен — UI показывает подсказку
   «запустите агент» вместо тихой ошибки.
5. **MCP-инструмент** `update_source_from_infobase(project_id, source_id)`
   — создаёт задание и возвращает его id; статус — через
   `get_index_status` (расширить сводкой по dump_jobs). Аннотации: не
   read-only; уточнить в описании, что выгрузка перезаписывает XML
   источника (штатно, `-update` инкрементален).
6. **Web UI**: в карточке источника — поля подключения, кнопка
   «Обновить из базы», индикатор задания, время последней выгрузки;
   расписание (ежедневно/cron) — планировщик в сервере (фоновый поток,
   проверка раз в минуту) создаёт задания сам.
7. **Ограничения, зафиксировать в README**: версия платформы агента
   должна быть совместима с версией базы; для `/S` нужна клиентская
   лицензия на машине агента; пароль в командной строке виден в списке
   процессов машины агента — рекомендовать отдельного пользователя ИБ
   с минимальными правами (только Конфигуратор/чтение конфигурации);
   файловая база должна быть доступна с машины агента локально.

Зависимости: этап 5 (иначе после выгрузки всё равно нужен report.txt)
и этап 4 (фоновые задания и инкрементальный reindex).

Критерии приёмки:
- файловая база: агент на Windows-хосте + сервер в Docker — кнопка
  «Обновить из базы» проходит цикл выгрузка → reindex без ручных шагов;
- клиент-серверная база: то же через `Srvr=...;Ref=...`;
- MCP: `update_source_from_infobase` создаёт задание, статус виден;
- расписание срабатывает и после выгрузки индекс актуален;
- пароль не появляется ни в projects.json, ни в логах, ни в UI.
