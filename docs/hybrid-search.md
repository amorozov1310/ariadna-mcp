# Гибридный поиск: карточки, замеры, решения

Рабочий документ шагов развития после 1.0 (см.
[ADR 0001](adr/0001-standalone-1x.md)). Здесь — то, что уже сделано и
измерено, и то, что из этого следует для следующих шагов.

## Карточка процедуры

`src/core/cards.py` строит карточку детерминированно, из индекса и файла
модуля, без LLM:

- **заголовок** — директива и подпись процедуры, модуль, объект метаданных
  и его синоним, область (`#Область`, вложенные через `/`), комментарий
  сразу над объявлением;
- **фрагменты тела** — строки процедуры подряд, каждый не длиннее
  `CHUNK_CHARS` (1500) символов, с номерами строк; хвост длинной процедуры
  уходит в следующие фрагменты, ничего не отбрасывается;
- **текст для индексации** — заголовок + фрагмент (по тексту на фрагмент);
- **`content_hash`** — отпечаток формата карточки (`CARD_FORMAT`), заголовка
  и тела: меняется код процедуры или синоним объекта — меняется отпечаток;
  код соседних процедур на него не влияет.

Файл модуля недоступен — карточка остаётся с одним заголовком
(`body_available=False`), процедура не пропадает.

Посмотреть карточки и замерить их на своём индексе:

```bash
python -m src.core.cards --project ID --show 3
docker exec ariadna python -m src.core.cards --project ID   # индекс в контейнере
```

## Замер карточек на реальных индексах

2026-10-30, контейнер Ариадны 1.0 на рабочей машине разработчика,
`CHUNK_CHARS=1500`. Конфигурации обезличены.

| Конфигурация | Карточек (процедур) | Фрагментов | С комментарием | Символов тел | Сборка |
|---|---:|---:|---:|---:|---:|
| Малая отраслевая | 701 | 829 | 4% | 0,5 млн | 0,8 с |
| Средняя с 11 расширениями | 4 348 | 5 082 | 16% | 2,9 млн | 3 с |
| Крупная типовая А | 543 060 | 754 362 | 13% | 572 млн | 130 с |
| Крупная типовая Б | 549 266 | 797 749 | 15% | 632 млн | 149 с |

Распределение на крупных: фрагментов на карточку в среднем 1,4 (p95 — 3,
максимум — 873 у одной процедуры); символов во фрагменте p50 ≈ 600,
p95 ≈ 1490; заголовок p50 ≈ 300, p95 ≈ 550 символов.

## Что из этого следует

- **Объём векторов.** ~800 тыс. фрагментов на крупную конфигурацию:
  при 384 измерениях это ~1,2 ГБ во float32 и ~0,3 ГБ в int8 на проект.
  Хранить на диске, в память — не всё сразу.
- **Время эмбеддингов — главный риск.** Первичный расчёт ~800 тыс.
  фрагментов по ~600–2000 символов на CPU займёт, по грубой оценке, часы.
  Измерить на шаге выбора модели; варианты сокращения — индексировать
  сначала экспортные процедуры и модули объектов, пересчитывать только
  изменившиеся по `content_hash`, фоновая очередь с приоритетом.
- **Комментарии редки** (4–16% процедур) — смысл в основном приходится
  извлекать из имён, синонимов объектов, областей и кода; ценность
  заголовка карточки выше, чем самих комментариев.
- **Лексическая ветка по карточкам.** Тексты тел — 0,6 млрд символов на
  крупную конфигурацию; дублировать их в обычной FTS-таблице нельзя.
  Шаг 4: contentless FTS5 по текстам карточек (как `module_text_fts`, но
  на уровне фрагмента и с BM25-рангом) и замер размера.
- **Сборка карточек** — ~2,5 мин на крупную конфигурацию за один проход;
  приемлемо как часть переиндексации, если делать её по изменившимся
  модулям.

## Лексический индекс по карточкам (шаг 4)

Сравнение вариантов FTS5 на крупной конфигурации Б (~800 тыс. фрагментов,
`scripts/bench_card_fts.py`):

| Вариант | Размер | Запрос p50 / p95 | Различных рангов в топ-20 |
|---|---:|---:|---:|
| фрагменты, `detail=none` | 89 МБ | 15 / 331 мс | 1 — ранжирования нет |
| фрагменты, `detail=column` | 162 МБ | 13 / 333 мс | 1 — ранжирования нет |
| фрагменты, `detail=full` | 192 МБ | 12 / 330 мс | 19 |
| только заголовки, `detail=full` | 68 МБ | 6 / 223 мс | 7 |

Без позиций BM25 не различает документы — порядок выдачи случаен. Выбрано:
одна contentless-таблица `card_fts(head, body)` с `detail=full`, заголовок
весит больше тела (`HEAD_WEIGHT` = 3), у процедуры в выдаче остаётся лучший
фрагмент.

Встроено в reindex фазой `cards` после разрешения вызовов: пересобираются
только модули с новыми процедурами (перепарсенные), со сменившимся
синонимом объекта или форматом карточки. В заголовок добавлено имя
процедуры и объекта, разбитое на слова («тип склада по умолчанию»): слитное
имя 1С для FTS — одно слово. Слова запроса короче трёх букв отбрасываются:
как префикс они совпадают с огромной частью словаря.

На копии индекса конфигурации Б (рабочая машина разработчика, без Docker):

- первичная сборка — 224 с, индекс +302 МБ (1181 → 1483 МБ);
- повторный reindex без изменений — 0,2 с на проверку карточек;
- запрос — 30–520 мс, на большинстве запросов 50–260 мс.

Наружу индекс пока не выведен (16 инструментов не меняются); он основа
лексической ветки будущего инструмента и стенда оценки (шаг 5).

## Стенд оценки (шаг 5)

`src/core/search_eval.py` сравнивает методы поиска на наборе вопросов с
известными правильными ответами — так, как агент вызвал бы поиск одним
запросом: `procedures` (`search_procedures`), `code` (`search_code`,
строка → процедура), `cards` (BM25 по карточкам). Метрики: hit@1/@5/@10,
MRR, задержка p50/p95, отдельно — отрицательные вопросы (правильный ответ
«в конфигурации этого нет»).

Набор — YAML/JSON, формат в докстринге модуля и в
`tests/fixtures/eval_ru.json`. Реальные наборы — в `data/eval/` (вне Git):

```bash
docker exec ariadna python -m src.core.search_eval /data/eval/myconf.yaml --details
```

Синтетический набор (20 вопросов к `xml_ru` + расширению):

| Метод | hit@1 | hit@10 | MRR | Своими словами (9), hit@10 |
|---|---:|---:|---:|---:|
| procedures | 39% | 39% | 0,39 | 0% |
| code | 22% | 39% | 0,28 | 0% |
| cards | 67% | 89% | 0,74 | 78% |

Точные имена все методы находят первыми. Промахи карточек — морфология:
«оформление заказа» не находит `ОформитьЗаказ`, «регистрация события» —
`ЗарегистрироватьСобытие` (префиксы «оформлени…»/«оформит…» и приставка
«за-» не совпадают). Это кандидаты на улучшение — лёгкий стемминг
запроса и карточек или векторная ветка; что выбирать, решают реальные
наборы вопросов, а не синтетика.

## Доработки ранжирования по итогам стенда

Набор из 35 вопросов к крупной конфигурации Б (типовые вопросы
разработчиков; правильные ответы найдены по именам процедур, не поиском по
карточкам; хранится локально, вне Git). Каждая доработка — отдельный замер:

| Вариант | hit@1 | hit@5 | hit@10 | MRR | p50 / p95 |
|---|---:|---:|---:|---:|---:|
| поиск по карточкам шага 4 | 24% | 42% | 52% | 0,31 | 81 / 378 мс |
| + корни слов в заголовке карточки | 27% | 45% | 64% | 0,34 | 88 / 454 мс |
| + точное имя первым | 30% | 52% | 70% | 0,39 | 87 / 452 мс |
| + корни в запросе | 33% | 61% | 70% | 0,44 | 256 / 940 мс |
| + бонус экспорта 0,15 | 39% | 64% | 79% | 0,50 | 263 / 901 мс |
| + вес заголовка 8 (было 3) | 42% | 64% | 79% | 0,52 | 271 / 985 мс |
| + точные имена по числу вызывающих | 48% | 64% | 79% | 0,56 | 282 / 1028 мс |
| + востребованность 0,03 | 48% | 73% | 79% | 0,58 | 268 / 1050 мс |
| + основы слов запроса (итог, 1.2.0) | 58% | 79% | 94% | 0,70 | 365–400 / 950–1190 мс |

Для сравнения на том же наборе: `search_procedures` — hit@10 12%,
`search_code` — 3%. На синтетическом наборе итог — hit@10 100%, MRR 0,93.

Что сделано (`src/core/cards.py`, `CARD_FORMAT` = 2):

- **корни** (`word_roots`) — первые 5 букв кириллических слов от 7 букв и
  то же без глагольной приставки: «отправление» и «отправить» → «отпра»,
  «зарезервировать» → «резер». В заголовке карточки — строка «Корни», в
  запросе — дополнительные термы. Грубая замена стемминга: лишние корни
  («правл» из «отправление») встречаются, но на стенде выигрыш больше.
  Цена — лишние термы в запросе: p95 вырос до ~1 с;
- **точное имя**: запрос из одного слова ищется и как имя процедуры;
  одноимённые идут по числу вызывающих в графе, затем экспортные методы
  общих модулей (исходный `ЗначениеРеквизитаОбъекта` с тысячами
  вызывающих — первым, его обёртки — после);
- **бонус экспорта** `EXPORT_BONUS` = 0,15 и **вес заголовка**
  `HEAD_WEIGHT` = 8;
- **востребованность** `POPULARITY_WEIGHT` = 0,03 × ln(1 + вызывающих) —
  предварительно: прирост на стенде — три вопроса из 33; при 0,15 качество
  падает.

Параметры подобраны на одном наборе — их стоит перепроверить на наборах
других конфигураций и на вопросах, проверенных человеком.

### Основы слов запроса

Корни (первые 5 букв) не покрывали слова из 6 букв и беглые гласные:
«расчет скидок» не находил `РассчитатьПоЧекуККМ` модуля `СкидкиНаценкиСервер`
(«скидок» — не префикс «скидки», у «расчет» корня не было). Теперь каждое
кириллическое слово запроса заменяется основой (`query_stems`):

- без окончания падежа, числа или формы глагола, если остаётся не меньше 4
  букв: «заказу» → «заказ», «почтовых» → «почтов»;
- без беглой гласной в суффиксах «-ок/-ек/-ец»: «скидок» → и «скидк»;
- с чередованием «расч» — «рассч»: «расчет» → и «рассч».

В запросе из нескольких слов терм, который продолжает другой терм
(«отправлени» при корне «отпра»), убирается: найденное он не расширяет, а
запрос замедляет. Без этого основы прибавляли к p95 ~0,3 с (1,1 → 1,4 с), с
этим — задержка прежняя, а качество выше (hit@10 85% → 94%). В запросе из
одного слова термы остаются — там важнее точность.

Меняется только запрос: карточки и `CARD_FORMAT` прежние, переиндексация
не нужна.

Что пробовали и не взяли (тот же набор):

| Вариант | hit@1 | hit@10 | MRR | Почему нет |
|---|---:|---:|---:|---|
| основы + исходные слова целиком | 52% | 82% | 0,60 | точная форма перевешивает остальные слова запроса |
| основы без удаления лишних термов | 58% | 85% | 0,69 | p95 1,4 с |
| + слова запроса, слитые в точное имя | 52% | 91% | 0,64 | «получить курс валюты на дату» → 11 одноимённых процедур форм отчётов выше общего модуля |
| + вся фраза отдельным термом | 55% | 91% | 0,67 | то же |

Цена: на синтетической фикстуре «тип склада по умолчанию» теперь ставит
`СкладПоУмолчанию` (экспортная, короче) перед `ТипСкладаПоУмолчанию` —
«склада» и «склад» совпадают. Точное имя по-прежнему находится первым.

## Поиск объектов метаданных своими словами

Помощнику по данным базы нужен не код, а объект, где лежат данные: «сколько
должны пайщикам» → регистр взаиморасчётов по аренде земельных долей. Набор
из 38 таких вопросов к отраслевой конфигурации (ответ — объект, стенд
`--methods metadata`) и 12 запросов-имён («Номенклатура», «Хозрасчетный»):

| Вариант `search_metadata` | вопросы к данным hit@1 / @5 / @10, MRR | имена hit@1 | p50 / p95 |
|---|---|---:|---:|
| было: все слова (AND), иначе LIKE по префиксам | 29% / 34% / 37%, 0,32 | 50% | 270 / 470 мс |
| любое слово по основам (OR), BM25 | 21% / 53% / 66%, 0,36 | — | 1 / 4 мс |
| + синоним ×6, имя ×3 | 29% / 63% / 68%, 0,44 | — | |
| + объекты с данными ×1,3 | 42% / 66% / 71%, 0,53 | — | |
| + лучший реквизит объекта ×0,5 | 53% / 76% / 82%, 0,62 | 50% | 4 / 11 мс |
| AND и LIKE первыми, затем ранжированный | 29% / 47% / 58%, 0,38 | | 289 / 620 мс |
| **итог**: точное имя → AND → ранжированный → LIKE, если пусто | 50% / 71% / 82%, 0,60 | 92% | 12 / 22 мс |

- Слова запроса, связанные через AND, на вопросе своими словами почти
  никогда не совпадают все сразу («сколько», «должны»), и тогда резервный
  LIKE по обрезанным префиксам приносил случайные объекты. Теперь LIKE —
  только если не нашлось вообще ничего.
- Реквизиты: «расход горючего», «себестоимость», «пробег», «координаты» — это
  ресурсы и измерения регистра, а не его синоним; лучший реквизит объекта
  добавляется к его рангу, объект, найденный только по реквизиту, тоже в
  выдаче.
- Объекты со всеми словами запроса остаются первыми — так запросы по имени
  ведут себя как раньше; среди объектов с именем, равным запросу, сначала
  справочники, документы и регистры.

Промахи, которые лексикой не закрыть: «долг по арендной плате за паи» (в
синониме «взаиморасчеты… земельных долей»), «где сейчас техника» (регистр
«Текущая позиция ОС»), «серверы спутникового мониторинга» («Серверы сбора
данных»), «список полей» (основа «пол» короче 4 букв), «НЗП» (аббревиатура).
Это кандидаты для векторного поиска или для переформулировки запроса самим
агентом.

### Слова вопроса и переформулировка

Короткий вопрос «сколько должны пайщикам» находил `Справочник.Должности`
(основа «долж»), а когда совпадений не было вовсе («сколько телят»), резервный
LIKE обрезал фразу до «ско» и приносил «НесКОЛЬко…». Теперь слова вопроса
(`cards.QUERY_STOPWORDS`) не ищутся, LIKE — только для запроса из одного слова,
и такой вопрос получает пустой ответ. На наборах метрики не изменились (это
чистка шума, а не новые попадания); короткие вопросы закрывает переформулировка
агентом — инструкция сервера просит искать словами, которыми объекты называют в
1С. Проверка на отраслевой конфигурации: «взаиморасчеты по аренде земельных
долей», «текущая позиция основного средства», «приплод животных», «НЗП» находят
нужный объект первым там, где исходные «пайщики», «трактор», «телята»,
«незавершенное производство» не находили ничего или находили не то.
