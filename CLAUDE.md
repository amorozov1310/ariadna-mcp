# Ариадна — памятка для работы с репозиторием

> Тот же материал дублируется в [AGENTS.md](AGENTS.md) — универсальном
> имени файла для агентов помимо Claude Code. При правке синхронизируйте
> оба файла.

MCP-сервер + Web UI: индексируют XML-выгрузку конфигурации 1С в SQLite
(FTS5) и дают агенту быстрый поиск по метаданным, коду BSL и графу
вызовов. Обзор и подключение агентов — [README.md](README.md), запуск —
[SETUP.md](SETUP.md).

## Главное про данные

**В репозитории нет каталога `data/`** — там лежат выгрузки конфигураций
заказчиков и `projects.json`, а при нативном запуске и индексы (гигабайты);
он в `.gitignore`. В Docker индексы лежат отдельно — на томе
`ariadna-index` (`INDEX_DIR=/index`, см. «Локальные особенности»). В свежем клоне
(в том числе в облачной сессии) нет ни одного проиндексированного
проекта: MCP-инструменты и Web UI будут работать, но покажут пустой
реестр, пока не добавлен источник.

Что это значит на практике:

- быстрые тесты не зависят от `data/` и проходят везде — они собирают
  индекс из фикстур во временном каталоге;
- slow-тесты (`-m slow`) требуют реальных корпусов в `data/projects/` и
  сами пропускаются, если их нет. В `data/` они ничего не пишут: выгрузки
  только читаются, а реестр, индексы и сгенерированный `report.txt` — во
  временном каталоге (`tests/corpus_sandbox.py`); после каждого теста
  проверяется, что записи его проектов в `data/projects.json`, их
  `report.txt` и `index.db*` в `data/projects/*/` не изменились (правки
  других проектов в Web UI во время прогона тест не роняют);
- проверять изменения парсера/поиска в облаке нужно на фикстурах
  (`tests/fixtures/`), а не на ERP.

## Команды

```bash
python -m pytest tests -q          # быстрые тесты, ~10 с, должны быть зелёными
python -m pytest tests -q -m slow  # только при наличии data/projects (локально)
python -m src.main                 # Web UI :9878, MCP :9879/mcp, SSE :9877/sse
```

Зависимости: `pip install -e ".[dev]"`, генерация отчёта из XML —
`pip install -e ".[xml-report]"`.

Список зависимостей — только в `pyproject.toml`: Docker-образ ставит их
офлайн из `docker-wheels/`, а `docker-wheels/fetch.sh` и `Dockerfile` берут
список оттуда (`scripts/docker_requirements.py`). После правки зависимостей
обновить колёса (из корня репозитория; на Windows — из PowerShell с полным
путём, Git Bash портит пути в `-v`):
`docker run --rm -v "$PWD:/repo" -w /repo python:3.12-slim sh docker-wheels/fetch.sh`.

CI (`.github/workflows/tests.yml`) прогоняет быстрые тесты на каждый push
и pull request — перед тем как просить смержить PR, убедитесь, что они
зелёные локально.

## Устройство

- `src/core/` — ядро: `xml_walker` (обход выгрузки) → `bsl_parser`
  (процедуры и вызовы, regex, без AST) → `indexer` (запись в SQLite,
  двухпроходная индексация + `resolve_calls`) → `search` (FTS5 + LIKE
  fallback), `call_analyzer` (деревья вызовов), `project_manager`
  (реестр проектов, фоновая переиндексация).
- `src/mcp_server/` — `server.py` регистрирует инструменты в MCP SDK,
  вся логика в `tools.py` (намеренно без импортов SDK — тестируется
  напрямую).
- `src/web/` — FastAPI + Jinja2, без сборки фронтенда.

## Соглашения

- Комментарии и тексты для пользователя — по-русски, как в остальном коде.
- Имена объектов 1С бывают русскими и английскими; сравнение всегда
  регистронезависимое через колонки `*_name_cf` (`casefold`), а не через
  `NOCASE` (он работает только для ASCII).
- Схема БД без миграций: при её изменении индекс пересоздаётся из
  исходников (`_recreate_if_stale_schema`).
- Пути к файлам модулей хранятся относительными с `/`; абсолютный
  `abs_path` — только запасной вариант, полагаться на него нельзя
  (индекс может быть построен на другой машине).
- Изменение кода парсера (`bsl_parser.py`/`bsl_reference.py`) само
  инвалидирует существующий индекс при следующем reindex (отпечаток
  парсера, `src/core/parser_fingerprint.py`) — вручную удалять
  `index.db` для проверки правки не нужно.

## Локальные особенности (не про облако)

На Windows с Docker каталог `data/` виден контейнеру через 9p: полный
проход по индексу там перечитывает файл при каждом вызове (секунды вместо
0,1 с), а блокировки и WAL SQLite через эту границу не работают. Поэтому в
Docker индексы лежат на именованном томе `ariadna-index`
(`/index/{id}/index.db`, `INDEX_DIR=/index`; путь строит
`ProjectManager._index_path`, сам класс переменную окружения не читает —
её передают `main.py` и `web/app.py`). При первом старте после обновления
старые `data/projects/*/index.db` один раз копируются на том
(`ProjectManager.migrate_index_dir`, backup API); сами они не удаляются —
их можно удалить вручную. Индекс с нуля — reindex проекта или
`docker volume rm ariadna-index`.

Прежнее правило «не открывать `data/projects/*/index.db` с хоста, пока
контейнер запущен» для Docker с `INDEX_DIR` больше не актуально: контейнер
эти файлы не читает, а его индекс с хоста напрямую не виден (только через
`docker compose exec`). Правило действует, если контейнер запущен без
`INDEX_DIR` — тогда сервер начнёт отвечать `unable to open database file`
(лечится `docker restart ariadna`). Выгрузки и `projects.json` у Docker и
нативного запуска общие, поэтому нативный запуск — при остановленном
контейнере. Slow-тесты в `data/` не пишут, для них контейнер останавливать
не нужно. Образ не подхватывает правки `src/` автоматически — нужен
`docker compose up -d --build`.
